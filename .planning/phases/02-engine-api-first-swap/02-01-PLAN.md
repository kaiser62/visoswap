<measured_facts>
Facts established by measurement during planning. Do not re-derive them; if one turns out to be
wrong, record the disagreement in the summary rather than silently working around it.

- `visoswap/models/models_data.py` line 6 sets the models directory to the **relative** string
  `./model_assets`, vendored verbatim. Every asset read in the engine is built from it by f-string
  at import or call time. There is no environment override until Phase 4.
- `models_list` holds **56** entries and `models_trt_list` holds **6**. The roadmap's Phase 4
  criterion says "54 tracked files" — that number does not match the manifest and Phase 4 should
  re-derive it rather than trust it.
- `ModelsProcessor.load_model` does **not** auto-download. The download call is commented out
  upstream at lines 131-132 of the vendored file, so a missing weight raises from
  `onnxruntime.InferenceSession` rather than starting a 12GB fetch. This is why linking, not
  downloading, is the right mechanism.
- `ModelsProcessor.__init__` constructs all seven sub-processors (lines 95-101). `FaceEditors`
  opens `liveportrait_onnx/lip_array.pkl` in its constructor, inside a `try`/`except
  FileNotFoundError` that leaves `lp_lip_array` as `None`. So the models directory must already
  resolve when the processor is **constructed**, not merely when a frame is swapped, and a
  silently `None` lip array is the failure mode of getting this wrong.
- Of the four `*_layout_data` modules, **only `face_editor_layout_data` imports clean with the
  seven Qt roots blocked**; `common_layout_data`, `swapper_layout_data` and `settings_layout_data`
  all reach PySide6. Measured with the same seven-root block Phase 1 uses. The layout dicts
  therefore cannot be imported by any Qt-free test, which is why the fixture is generated once,
  offline, and checked in.
- Key counts, measured by flattening the four dicts: common 23, swapper 103, face_editor 42
  (project tier = **168**), settings **33** (global tier), **overlap 0**. These match the design.
- The layout dicts' `default` values are **strings**, not typed values: `ClipAmountSlider` default
  is the string `50`, `SimilarityThresholdSlider` default is the string `60`,
  `FaceEditorCropScaleDecimalSlider` default is the string `2.50`. The same is true of
  `profiles.json`, whose two entries each carry an `options` dict of 33 keys and a `parameters`
  dict of 168 keys with 138 string values and 30 bool values. **The design's phrase "typed default
  where the widget has one" therefore means derived from widget shape, not read from `default`.**
- Widget shape is fully mechanical and was measured across all 201 keys. Exactly four shapes
  exist: `decimals` present alongside min/max/step (42 keys, float); min/max/step without
  `decimals` (94 keys, int); an `options` list (selections, str); neither (toggles, bool).
- `DFMModelSelection` is the one key whose `default` and `options` are **callables**
  (`get_dfm_models_default_value`, `get_dfm_models_selection_values` in
  `app/helpers/miscellaneous.py`, deliberately not vendored). It resolves against the models
  directory at runtime.
</measured_facts>

  <action>
Write `tools/link_model_assets.py`, a project-authored, dependency-free script (standard library
only, no torch, no Qt) that creates a directory link at the repository root named `model_assets`
pointing at a source directory, and can also verify one.

Resolution order for the source: the `VISOSWAP_MODEL_ASSETS_SOURCE` environment variable, else
`D:/Visomaster/model_assets`. Record the resolved source in the script's output so a wrong link is
diagnosable from the log alone.

Behaviour: `--check` verifies the link exists, resolves to a directory, and that a named probe set
of files is readable through it, exiting non-zero with the missing names listed if not. With no
flag it creates the link. Creating over an existing real directory must refuse and exit non-zero —
overwriting a real directory of weights is the one unrecoverable mistake this script can make.
Creating over an existing link that already points at the resolved source is a no-op success.

On Windows use a directory junction, created by invoking the shell's `mklink /J` through
`subprocess`; junctions do not require administrator rights, whereas symbolic links do. On POSIX
use `os.symlink`. Detect by `os.name`, not by guessing from a path string.

The probe set `--check` verifies is the exact set the Phase 2 swap path reads, named explicitly so
a later phase can shrink or widen it deliberately: `det_10g.onnx` (the RetinaFace detector),
`w600k_r50.onnx` (the Inswapper128ArcFace recogniser), `inswapper_128.fp16.onnx` (the swapper),
`occluder.onnx` and `XSeg_model.onnx` (the two mask models), `faceparser_resnet34.onnx` (the face
parser), `meanshape_68.pkl` (the 3d68 landmark mean shape), `liveportrait_onnx/lip_array.pkl` and
`liveportrait_onnx/motion_extractor.onnx` (the LivePortrait entry assets).

Do **not** add `rd64-uni-refined.pth` to the probe set. It is required by the CLIPseg mask path and
it does not exist anywhere under `D:/Visomaster`, nor in the 56-entry model manifest. Plan 02-04
owns that gap; a check that fails from day one teaches everyone to ignore the check.

Write `docs/engine-test-assets.md` recording: that the models directory is a relative path baked
into vendored code until Phase 4 and therefore the runner's working directory is load-bearing; that
the link is the mechanism by which 12GB is reached without copying; the probe set above with what
reads each file; that `model_assets/` and `tensorrt-engines/` are already ignored by git so the
link is never committed; and that the link is intended read-only — nothing in Phase 2 may write
through it into the source tree.

Confirm `.gitignore` already carries `model_assets/` and `tensorrt-engines/` and add them only if
absent. It carried both at planning time; changing a file that already says the right thing is
churn.

<task type="auto">
  <name>Task 3: Seal the runner against Qt, VisoMaster and the backend</name>
  <precondition>`tests/_qt_guard_probe.py` exists and its seven blocked Qt roots are readable from `tests/conftest.py`.</precondition>
  <files>tests/_engine_runner.py, tests/conftest.py, tests/test_engine_seal.py</files>
  <action>
Write `tests/_engine_runner.py`, a standalone script run as a subprocess and **never imported by
pytest** — the same shape as `_qt_guard_probe.py`, for the same reason: the interpreter that runs
pytest has no torch, and the interpreter that has torch also has Qt.

Before any other import, install a `sys.meta_path` finder at index 0 that raises `ImportError` for
three groups of roots. The seven Qt roots Phase 1 established. The VisoMaster application package
root. The backend package root. Blocking the second and third is what turns roadmap criterion 3
from a text search into a runtime proof: engine code cannot reach either even when both are
installed and importable.

Reuse the Qt root list rather than retyping it — lift it into `tests/conftest.py` as a shared
constant next to `PENDING_QT_STRIP` and have the runner read it from there, in the same spirit as
plan 01-02's single shared exclusion set. Two copies of a block list is how the two gates silently
diverge.

Report through exit codes, extending the probe's vocabulary so a harness fault is never readable as
an engine pass: 0 clean, 1 a blocked root was reached or leaked into the loaded-module table, 2 an
engine dependency is missing, 3 a required asset or fixture is missing, 4 any other engine error.
Print one machine-readable line before exiting so pytest can attribute a failure without parsing a
traceback.

Give it a self-test mode that arms the seals, asserts each of the three groups actually raises when
provoked, imports nothing from the engine, and exits 0. Later plans add real modes; this plan
proves only that the seal is armed and capable of failing.

Then write `tests/test_engine_seal.py` with three tests. First, the self-test mode exits 0 on the
engine interpreter. Second, the runner is proven capable of exit 1 by asking it to import a Qt
module directly. Third, a static scan over every source file under `visoswap/` that finds any
import of the backend package and fails naming file and line — reusing `vendored_sources()` and the
comment-stripping approach from `tests/test_no_qt_source.py` so a mention inside a removal note is
not a hit, and asserting the scanned file list is non-empty so an empty tree cannot pass vacuously.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository → `D:/Visomaster` | A filesystem link is created from a writable repo into a tree declared read-only source material. Anything a test writes through the link lands in that tree. |
| generator → layout dicts | `tools/dump_engine_settings.py` executes third-party Python from the VisoMaster checkout with Qt available, to produce a file the sealed runner later trusts. |
| checked-in fixture → engine | `tests/fixtures/engine_settings.json` is the only settings source the engine is given. A wrong value here is executed, not validated. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `tools/link_model_assets.py` creating over an existing directory | high | mitigate | Refuse and exit non-zero when the target exists and is a real directory rather than a link; never delete or overwrite a directory. |
| T-02-02 | Tampering | Writes through the link into `D:/Visomaster/model_assets` | high | mitigate | Nothing in Phase 2 writes through the link; the TensorRT cache path is avoided by selecting the CUDA provider in plan 02-02, and every plan's verification re-runs Phase 1's unmodified-source check on `D:/Visomaster`. |
| T-02-03 | Elevation of Privilege | `mklink` invoked through a shell | medium | mitigate | Junction (`/J`) not symlink, so no elevated rights are requested; the source path is passed as an argument list rather than interpolated into a shell string. |
| T-02-04 | Tampering | `tools/dump_engine_settings.py` importing and executing VisoMaster UI modules | medium | accept | The checkout is already trusted as the source of 10.6k vendored lines; the generator runs offline in development, never on a user machine, and its output is reviewed as a checked-in diff. |
| T-02-05 | Spoofing | A blocked root resolved from a stale copy of the block list | medium | mitigate | One shared constant in `tests/conftest.py` read by both the probe and the runner; `tests/test_engine_seal.py` proves the seal is capable of exit 1 rather than assuming it. |
| T-02-06 | Information Disclosure | Runner output containing absolute media or model paths in logs | low | accept | Single-user local project; paths are already in the plan and the docs. No image payload is ever logged. |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan introduces **no** new third-party package: `tools/` scripts are standard library only, and the generator and runner use packages already present in the engine interpreter. If an install becomes necessary, halt and require the package-legitimacy gate plus a blocking human checkpoint before proceeding. |
</threat_model>
