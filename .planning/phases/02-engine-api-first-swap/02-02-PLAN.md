<measured_facts>
Measured during planning against `D:/Visomaster`. Plan against these; do not re-derive.

**The exact surface `frame_worker` needs from a detected face.** Counted over the whole 1,306-line
file, the values of the target-face mapping are touched at exactly three members and nothing else:
`face_id` (4 sites), `get_embedding(recognition_model_name)` (4 sites) and
`assigned_input_embedding` (1 site, a mapping of arcface model name to ndarray). The mapping itself
is iterated at five sites. Upstream's `TargetFaceCardButton` carries far more — a media path, a Qt
checkable state, a context menu, an assigned-input-faces dict, an assigned-merged-embeddings dict —
and none of it is read by the swap pipeline. `FaceCard` therefore needs three members, one
constructor input for the crop, and the merge helper described below.

**How the source embedding reaches the swap.** At frame_worker line 181 the swap is called with
`s_e` taken from `assigned_input_embedding` keyed by the arcface model that
`get_arcface_model(parameters['SwapModelSelection'])` returns, and `t_e` taken from the target's own
`get_embedding` for the same arcface model. `arcface_mapping_model_dict` maps `Inswapper128` to
`Inswapper128ArcFace`. Upstream computes `assigned_input_embedding` in
`calculate_assigned_input_embedding`, which merges every assigned source store per model by mean or
median according to the global `EmbMergeMethodSelection` key. With one source face the merge is the
identity, but implement the merge rather than the shortcut — the mean of one is one, and Phase 3
will assign more than one.

**Detection is a four-call sequence,** established by `card_actions.find_target_faces` and confirmed
by `inprocess.py`. Read a frame as BGR, flip to RGB, move to the processor's device as a uint8
tensor permuted to channel-first, call `run_detect` with the nine control keys it takes, then call
`run_recognize_direct` once per detected keypoint set to get an embedding and a crop. Dedupe by
cosine distance against the cards already collected, using the per-face similarity threshold. Build
the per-card embedding store by running `run_recognize_direct` once for **each** of the four
recognition options — `Inswapper128ArcFace`, `SimSwapArcFace`, `GhostArcFace`, `CSCSArcFace` —
because the swapper model chosen at swap time decides which one is read, and it need not be the one
detection ran under.

**The crop channel order is a trap with a measured consequence.** `run_recognize_direct` returns an
RGB crop; upstream flips it to BGR before storing it on the card. The reference
`faceselect.classify_crop` then flips it back to RGB for the gender classifier, and its docstring
records that feeding the stored BGR straight through flipped a face's label between adjacent frames.
Store the crop BGR, matching upstream, and say so in the dataclass docstring.

**The processed frame has no exit route.** Plan 01-04 deleted the display path from
`frame_worker.run()`, so the swapped frame is left on the worker instance. `visomaster_headless.process_frame`
sidesteps `run()` entirely: it constructs a worker, assigns `parameters` and the target-face mapping
onto it, and calls `process_frame()` directly, which returns the frame. Do the same. Do not call
`run()`.

**Provider choice is a correctness decision, not a performance one.** `ModelsProcessor` defaults to
TensorRT, whose execution-provider options write an engine and timing cache into a **relative**
`tensorrt-engines` directory. With the working directory at the repository root that creates a new
cache and a multi-minute first-inference build; with it anywhere near the source tree it writes into
read-only material. Select CUDA via `switch_providers_priority`, which the vendored file supports
alongside TensorRT, TensorRT-Engine and CPU. The reference implementation measured 21.2 fps on CUDA
against 27.8 on TensorRT at 1080p — irrelevant for a smoke test, and the reason is worth recording
so a later phase can revisit it deliberately.

**Fixture media, named concretely.** Target video `D:/Visomaster/output/17f0d620_rosh_generate_135bda4c9686.mp4`
(672 KB, the smallest real face-bearing clip on the machine). Source face
`D:/Visomaster/inputt/598004cb_tonima.JPG` (42 KB). They are **deliberately different people**: the
video already contains the face from `17f0d620_rosh.jpg`, so using that image as the source would
swap a face onto itself and the non-zero-diff assertion would be testing nothing while appearing to
pass. Both are personal media and neither is committed.

  <action>
Write `visoswap/engine.py`, project-authored (no vendor attribution header — mirror how
`context.py` is exempted in the header gate, and extend that exemption rather than inventing a
second mechanism).

Define `FaceCard` as a dataclass with an embedding store mapping recognition-model name to ndarray,
a BGR crop, and an `assigned_input_embedding` mapping arcface-model name to ndarray. Give it a
`get_embedding` accessor returning the stored embedding or an empty array, matching upstream's
behaviour for a missing model exactly. Give it an `assign` method that takes source embedding stores
and a merge method name and computes `assigned_input_embedding` by mean or median per model, the
same shape as upstream's merge.

Expose `face_id` as a **derived, content-addressed** property, not a stored UI identifier: a stable
digest of the card's recognition embedding under the detection-time recognition model. This is the
one place the design's constraint bites — the roadmap requires no identifier tied to a UI element,
and Phase 3 requires the per-face tier keyed by recognition embedding. Deriving it here satisfies
both and means the same face in the same video always keys the same way. Document that a
near-duplicate embedding produces a different key, that dedupe by cosine distance during detection
is what prevents that from mattering, and that Phase 3 replaces exact-digest keying with threshold
matching.

Define `Engine` with a constructor taking a device and the two settings tiers, and three public
methods matching the design exactly. The constructor builds an `EngineContext` with the global tier
as `control`, an empty project-tier mapping as `parameters`, an empty target-face mapping, the
constructed models processor, an empty DFM metadata mapping, swap enabled and edit disabled;
switches the provider to CUDA; and sets the thread count from the global tier.

`load` opens the video, records its frame rate and frame count, and holds a single decoder guarded
by a lock. Read sequentially and only seek when the requested frame is not the one the decoder is
already sitting on — the reference implementation measured 0.230s for a seek against roughly 0.030s
for the next sequential read, and a per-frame seek is the difference between a usable engine and an
unusable one. `load` performs no detection.

`detect_faces` runs the four-call detection sequence from the measured facts at a caller-supplied
frame number, deduping by cosine distance against the per-face similarity threshold, and returns a
list of `FaceCard`. Sample more than one frame before giving up: frame 0 is routinely a black frame
or a title card, and the reference implementation records a whole 96-second clip failing every frame
for exactly that reason. Use fractional positions across the clip rather than fixed indices so the
spread means the same thing on a 10-second clip and a 90-minute one. Populate the context's
target-face mapping keyed by each card's derived id, and create a per-card entry in the context's
parameters mapping holding the full 168-key project tier — frame_worker reads the settings of the
**target face**, not a global set, so a missing entry raises rather than falling back.

`swap` takes a frame number, a source face image path and a settings mapping. It loads the source
image, detects exactly one face in it and takes that face's embedding store, assigns it to every
card via the merge, applies the caller's settings over the project tier for every card, decodes the
requested frame, and drives it through the frame worker directly rather than through the worker's
thread entry point. Return a contiguous BGR ndarray.

Do not populate `dfm_models_data`. Note 2 of the Phase 1 context surface flags who fills it as
Phase 2's call, and the answer this plan gives is: **not the tracer**. It stays empty here, because
filling it requires a directory scan for model files that do not exist on this machine and inventing
that now would be inventing it blind. That answer is already settled — see
`02-DECISION-deferred-paths.md`, which descopes the DFM path for Phase 2 and assigns the populator
for `EngineContext.dfm_models_data` to **Phase 4's model bootstrap**, where the model inventory
becomes explicit and verifiable. Plan 02-04 only records the gap; it does not decide it.

Do not add a field to `EngineContext`. If the tracer appears to need an eighth field, stop and record
why in the summary — that dataclass is pinned by a test on purpose.

Keep `visoswap/__init__.py` import-free as plan 01-01 established. Callers import from
`visoswap.engine` explicitly; an eager re-export would drag torch into every import of the package.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → `Engine.load` / `Engine.swap` | Both take filesystem paths. The engine is a library and its callers in Phase 4 will pass user-influenced values. |
| video/image file → decoder | Untrusted container and codec data is parsed by the decoder and the image reader before any engine code sees a pixel. |
| settings mapping → inference | The caller's settings mapping is applied over the project tier and read directly by the frame worker with no validation. |
| linked models directory → inference | Model files are loaded from a directory reached through a link created in plan 02-01. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Tampering | Path traversal through `Engine.load` / `Engine.swap` source argument | high | accept | The engine is a library with no notion of a project root; the reference implementation puts this check at the generator boundary and the roadmap assigns that boundary to Phase 4. Record explicitly in the engine module docstring that path validation is the caller's responsibility, and carry it into Phase 4's threat register so the acceptance is inherited deliberately rather than forgotten. |
| T-02-08 | Denial of Service | A crafted video or image consuming unbounded memory or time in the decoder | medium | mitigate | Only single frames are ever decoded — never the whole video — which is invariant 5 of the project's own rules; the max-faces control bounds the detection loop; the smoke test asserts a bounded wall-clock. |
| T-02-09 | Tampering | Writes into the read-only source tree through the models link | high | mitigate | CUDA provider selected so no TensorRT engine or timing cache is written; artifacts are written only under `tests/artifacts/`; plan verification re-runs the unmodified-source check on `D:/Visomaster`. |
| T-02-10 | Information Disclosure | Face crops and swapped frames written to disk and possibly committed | medium | mitigate | `tests/artifacts/` added to `.gitignore` in the same task that creates it; no image payload is ever logged, per the project's own logging convention. |
| T-02-11 | Tampering | An unvalidated caller settings mapping reaching inference | medium | mitigate | Overrides assert key membership in the generated fixture before assignment, so an unknown key fails loudly at the boundary. Full typed validation is SCHEMA-01, Phase 3. |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new third-party package: torch, onnxruntime and the image/video decoder are all already present in the engine interpreter and already used by vendored code. If an install becomes necessary, halt and require the package-legitimacy gate plus a blocking human checkpoint. |
</threat_model>
