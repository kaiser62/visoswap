<measured_facts>
Measured during planning. These are the facts the decision below rests on; do not re-derive them,
and if one is wrong, say so before acting on it.

**The text-masking path needs a file that does not exist anywhere.** `face_masks.run_CLIPs`
constructs a CLIPseg dense-prediction model and immediately loads `rd64-uni-refined.pth` from the
models directory. A whole-tree search of `D:/Visomaster` finds no file matching that name, finds no
serialized-tensor file of any name outside the bundled interpreter's site-packages, and the string
does not appear anywhere in `visoswap/models/models_data.py`. The manifest holds 56 model entries
and 6 TensorRT entries and none of them is this file. The conclusion is that **upstream VisoMaster's
text-masking control is non-functional on this install too** — not that something was lost in
vendoring.

**The text-masking path also reaches the network on first use.** The CLIPseg base constructor calls
into the vendored CLIP library to load the ViT-B/16 model, which downloads roughly 335 MB from a
public endpoint into a per-user cache directory. That cache is empty on this machine. The vendored
downloader verifies a SHA-256 digest that is embedded in the URL path and raises on a mismatch, so
the transfer is integrity-checked; it is still a first-run network dependency inside what is
otherwise an offline engine, and it must be stated in the docs rather than discovered by a user on a
plane. Plan 01-02 flagged the bundled byte-pair vocabulary as placement-verified but
resolution-unverified; this is the run that verifies it.

**The DFM path has no model files and no populator.** `model_assets/dfm_models/` contains only a
placeholder marker file. A whole-tree search finds no file with the DFM extension anywhere. Separately,
`EngineContext.dfm_models_data` is carried but never filled: upstream fills it from a helper in
`app/helpers/miscellaneous.py` that scans a directory, which plan 01-02 deliberately did not vendor
because directory discovery is not an inference concern, and note 2 of the Phase 1 context surface
assigns the question to Phase 2. Plan 02-02 deliberately left it empty rather than inventing a scan
for a directory with nothing in it. `models_processor.load_dfm_model` indexes that mapping by the
selected model name and raises on a miss.

**A DFM file is an ONNX model, not a pickle.** `DFMModel.__init__` hands the path straight to an
inference session. So the deserialization threat class here is a malicious ONNX graph parsed by the
runtime, not arbitrary code execution through unpickling — a materially lower severity than the
CLIPseg weights file, and worth knowing before the decision is framed.

**The swapper selection that reaches the DFM path** is the string `DeepFaceLive (DFM)` in the
project-tier swapper-model key. The arcface mapping sends it to the Inswapper128ArcFace recogniser,
so no additional recognition model is needed. At frame_worker line 171 the source embedding is
deliberately skipped for this swapper and the DFM model name is read from the project tier instead —
which is the only place in the pipeline where the swap runs on a model file rather than an embedding.

**Everything else in the frame worker's mask chain is already available.** The occluder, XSeg and
face-parser models are all present in the weight set, so the masking path can be exercised in every
respect except the text-driven part.
</measured_facts>

  <context>
Roadmap criterion 4 requires the smoke test to exercise the DFM swap-model path, the LivePortrait
editor path and the CLIPseg masking path at least once each. Plan 02-03 proved LivePortrait. The
other two cannot run: `rd64-uni-refined.pth` does not exist anywhere on this machine and is not in
the manifest, and there is no DFM model file anywhere on this machine.

This is not a difficulty judgement and it is not a scope reduction — it is a missing-information
blocker, which is one of the only three legitimate reasons to stop and ask. Both paths would be
planned without hesitation if the weights existed.

Two further consequences ride on the answer. First, Phase 4's BACKEND-01 refuses to start on an
incomplete model set; any asset added here has to be added to what that bootstrap checks, so the
answer defines part of Phase 4's scope. Second, the DFM half also decides who populates the DFM
metadata mapping on the context object, a question Phase 1 explicitly deferred to Phase 2 and that
plan 02-02 explicitly declined to answer blind.

Each path can take a different option; they are independent.
  </context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → weights file | Assets fetched from outside the project's own manifest, with no existing provenance in this repository. |
| public internet → CLIP model cache | The text-masking path downloads a 335 MB model into a per-user cache on first use, implicitly. |
| weights file → deserializer | The CLIPseg refined weights are deserialized by the vendored mask code. |
| DFM model file → inference runtime | An ONNX graph from a third party is parsed and executed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-17 | Tampering | `rd64-uni-refined.pth` fetched from outside the model manifest | critical | mitigate | Source nominated by the developer at a blocking decision checkpoint, never chosen by the agent; SHA-256 measured after download and recorded; partial files deleted on mismatch; the loading call already passes the safe-loading keyword, so even a substituted file cannot execute code during load. |
| T-02-18 | Tampering | DFM model file fetched from outside the manifest | high | mitigate | Same nominate-verify-record flow. Lower severity than T-02-17 because the file is an ONNX graph handed to an inference session rather than a pickle, so the exposure is a malicious graph rather than arbitrary code at load time. |
| T-02-19 | Spoofing | Implicit CLIP ViT-B/16 download on first text-masking use | medium | mitigate | The vendored downloader verifies a SHA-256 embedded in the URL path and raises on mismatch — verified by reading it, not assumed. Documented as an explicit first-run network dependency in the extra-asset document so it is a known cost rather than a surprise. |
| T-02-20 | Denial of Service | First-run download stalling the engine inside an inference call | medium | accept | Single-user local project and a one-time cost; the alternative, pre-fetching at construction, would slow every engine start for a control that is off by default. Recorded so Phase 4 can decide differently when the engine runs under a server. |
| T-02-21 | Tampering | Fetched assets written through the models link into read-only source | high | mitigate | Fetch tool writes only to the ignored asset location or a developer-named path, never through the link; each plan's verification re-runs the unmodified-source check on `D:/Visomaster`. |
| T-02-22 | Repudiation | The ledger table and its JSON block diverging when edited by hand | low | mitigate | Resolve the item through the ledger tool's own verbs, never by editing the file directly. |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new third-party package is expected. Weight files are **not** packages and are covered by T-02-17 and T-02-18 instead. If a package install does become necessary, halt and require the package-legitimacy gate plus a blocking human checkpoint; legitimacy checkpoints are never auto-approvable. |
</threat_model>
