<measured_facts>
Measured during planning. These are the facts the record below rests on; do not re-derive them, and
if one is wrong, say so before acting on it.

**The text-masking path needs a file that does not exist anywhere.** `face_masks.run_CLIPs`
constructs a CLIPseg dense-prediction model and immediately loads `rd64-uni-refined.pth` from the
models directory. A whole-tree search of `D:/Visomaster` finds no file matching that name, finds no
serialized-tensor file of any name outside the bundled interpreter's site-packages, and the string
does not appear anywhere in `visoswap/models/models_data.py`. The manifest holds 56 model entries
and 6 TensorRT entries and none of them is this file. The conclusion is that **upstream VisoMaster's
text-masking control is non-functional on this install too** — not that something was lost in
vendoring.

**The text-masking path would also reach the network on first use.** The CLIPseg base constructor
calls into the vendored CLIP library to load the ViT-B/16 model, which downloads roughly 335 MB from
a public endpoint into a per-user cache directory (`~/.cache/clip`). That cache is empty on this
machine. The vendored downloader verifies a SHA-256 digest embedded in the URL path and raises on a
mismatch, so the transfer would be integrity-checked. **Nothing in Phase 2 now triggers it**, because
the path is never constructed — but it stays documented, because a latent implicit 335 MB download
inside an otherwise offline engine is exactly the kind of thing that becomes a mystery six months
later, and Phase 4 must know about it before re-enabling the path.

**The DFM path has no model files and no populator.** `model_assets/dfm_models/` contains only a
placeholder marker file. A whole-tree search finds no file with the DFM extension anywhere. Separately,
`EngineContext.dfm_models_data` is carried but never filled: upstream fills it from a helper in
`app/helpers/miscellaneous.py` that scans a directory, which plan 01-02 deliberately did not vendor
because directory discovery is not an inference concern. Plan 02-02 deliberately left it empty rather
than inventing a scan for a directory with nothing in it, and per the decision of record the
populator belongs to Phase 4's model bootstrap. `models_processor.load_dfm_model` indexes that
mapping by the selected model name and raises on a miss.

**A DFM file is an ONNX model, not a pickle.** `DFMModel.__init__` hands the path straight to an
inference session. So the deserialization threat class there is a malicious ONNX graph parsed by the
runtime, not arbitrary code execution through unpickling — worth recording for whoever re-enables it.

**The swapper selection that reaches the DFM path** is the string `DeepFaceLive (DFM)` in the
project-tier swapper-model key. The arcface mapping sends it to the Inswapper128ArcFace recogniser,
so no additional recognition model would be needed. At frame_worker line 171 the source embedding is
deliberately skipped for this swapper and the DFM model name is read from the project tier instead.

**Everything else in the frame worker's mask chain is already available.** The occluder, XSeg and
face-parser models are all present in the weight set, so the masking path is exercised in every
respect except the text-driven part.

**Roadmap criterion 4 has no blocker.** As corrected, it names the LivePortrait editor path alone and
states that DFM and CLIPseg are import-proven only, by decision. Plan 02-03 satisfied it in full.
Nothing in this plan is criterion-4 work.
</measured_facts>
