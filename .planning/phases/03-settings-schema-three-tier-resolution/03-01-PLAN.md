<objective>
Turn VisoMaster's four Qt-bound layout dictionaries into one checked-in, typed `schema.json`, and
prove on the thinnest possible path that a value written at the project tier and then at the face
tier resolves in the right order with its type intact.

Purpose: today a setting's type lives in a Qt window — `main_window.default_parameters` at
`app/ui/main_ui.py:67`, which `visomaster_headless.py:88-89` coerces every incoming value against.
Every `default` in the layout dicts is a string, and so is every value in `profiles.json`. The whole
point of this phase is to move type out of the window and into the data. This plan is where that
move happens and where the three-tier spine that Phases 4 and 5 build on gets its shape.

Output: `tools/generate_schema.py` (offline, Qt interpreter), the committed
`visoswap/schema/schema.json`, a Qt-free loader, the settings DDL and the resolution function.

Measured during planning against `D:/Visomaster`. Plan against these; do not re-derive them.

**Key counts, confirmed by flattening the four dicts.** common 23, swapper 103, face_editor 42 —
the project tier, **168**. settings **33** — the global tier. **201** total, **zero overlap**
between the two tiers. These match the design and match what plan 02-01 measured independently.

**Three of the four layout modules reach PySide6 on import.** Measured with the same seven-root
block Phase 1's gate uses: `swapper_layout_data`, `common_layout_data` and `settings_layout_data`
all fail; only `face_editor_layout_data` comes through clean. This is why the generator lives in
`tools/` and not under `visoswap/` — `tests/conftest.py` walks every `.py` under `visoswap/` and
imports it with Qt blocked, so a generator placed there would fail the Phase 1 gate by design.
Plan 02-01 put `dump_engine_settings.py` in `tools/` for exactly this reason; follow it.

**Widget shape is fully mechanical and there are five shapes, not four.** Plan 02-01 already
derived and implemented this in `tools/dump_engine_settings.py`, whose `shape_of()` is the
authority:

  - `decimals` alongside min/max/step — 42 keys, float
  - min/max/step without `decimals` — 93 keys, int
  - min/max with **no** `step` — 1 key, text. `ClipText` is the only one; its `min_value` of `'0'`
    and `max_value` of `'1000'` are character-count bounds on a line edit and its default is the
    empty string. Typing it int does not merely mislabel it, it raises, because `int(float(''))`
    raises. `step` is the discriminator: a slider has one, a text box does not. It is also the only
    key carrying `width`.
  - an `options` list — 22 keys, selection
  - none of the above — 43 keys, toggle

  93 + 42 + 43 + 22 + 1 = 201.

**Default types in the raw dicts: 157 str, 43 bool, 1 callable. Zero numeric.** So a typed default
is *derived from shape*, never read from the type of `default`. `SimilarityThresholdSlider` is the
string `'60'`, `FaceEditorCropScaleDecimalSlider` is the string `'2.50'`, `ClipAmountSlider` is the
string `'50'`. `min_value` and `max_value` are strings too while `step` is already numeric, so a
single spec routinely disagrees with itself about type.

**The name convention is wrong and the web UI trusts it.** `webui2/app.js:145-159` picks a control
by substring: a key containing `Toggle` renders a checkbox, one containing `Selection` renders a
select, and **everything else falls through to a range slider**. Line 179 then parses the value with
`Number` if the key contains `Decimal` and `parseInt` otherwise. `ClipText` contains none of those
substrings, so today it renders as a slider from 0 to 1000 over a text field. That is the concrete
failure this phase's explicit `type` exists to prevent, and it is why type must never be inferred
from a key name again.

**Gating has two mechanisms and it is transitive but shallow.** 140 keys carry `parentToggle`, 4
carry `parentSelection`. `requiredToggleValue` is `True` for all 140 without exception. All four
`parentSelection` gates point at `SwapModelSelection`: `SwapperResSelection` requires
`Inswapper128`, and `DFMModelSelection`, `DFMAmpMorphSlider` and `DFMRCTColorToggle` each require
`DeepFaceLive (DFM)`. `parentToggle` is a plain string carrying two undocumented compound forms:
comma-separated in 2 keys (`OccluderXSegBlurSlider`, `RestoreEyesMouthBlurSlider`) and
pipe-separated in 3 keys (the three `FaceExpression...` sliders). 8 keys have a parent that is
itself gated; maximum chain depth is 2 and there are no cycles.

**Gating is presentational, not a value filter.** `frame_worker.py` reads `parameters[key]`
unconditionally and gates behaviour by reading the parent toggle itself — for example it reads
`ViewFaceMaskEnableToggle` and `ViewFaceCompareEnableToggle` directly at lines 73, 751, 757 and
1280. So `visible_when` in the schema tells a renderer what to hide; resolution must still return a
value for a key whose gate is closed. Anything else would change engine behaviour.

**`DFMModelSelection` is the only key with a callable `options` and a callable `default`.** They are
`get_dfm_models_selection_values` and `get_dfm_models_default_value` in
`app/helpers/miscellaneous.py`, deliberately not vendored. `get_dfm_models_data()` lists
`DFM_MODELS_PATH`, which is the **relative** path `./model_assets/dfm_models`, and keeps files
ending `.dfm` or `.onnx`, mapping filename to path. The options are those filenames; the default is
the first one, or the empty string when the directory is empty. Calling it during planning raised
`WinError 3` because that relative directory does not exist from the repository root — which is
precisely why a frozen list would be worthless and the roadmap requires it resolved at startup.

**The current serializer resolves callables eagerly and swallows the failure.**
`web_ui.py:648-664` calls any callable value at request time and, on exception, substitutes `[]` for
`options` and the empty string otherwise. So today a missing models directory silently produces an
empty dropdown with no error. It also drops every key starting `exec_`, which is the mechanism by
which the side-effect handlers went missing.

**The reference backend declares its schema as one SQL string.**
`backend/models/database.py` holds a module-level `SCHEMA` of `CREATE TABLE IF NOT EXISTS`
statements executed on connect, plus an additive `_migrate()` driven by `PRAGMA table_info`. It
enables `journal_mode=WAL`, `foreign_keys=ON` and `busy_timeout=5000` on connect. Match that shape
so Phase 4 can append rather than reconcile.

an int without a second coercion step, and it is the difference between this design and the one it
replaces. Give the two project-scoped tables and the identity table a foreign key onto `projects(id)`

DDL applies cleanly in a database that has no `projects` table yet; the function must not turn
`PRAGMA foreign_keys` on itself, since whether referential integrity is enforced is the connection
owner's decision and in Phase 4 that owner is the backend. Record both of those facts in a comment
next to the DDL — a future reader who does not know them will either add a spurious `projects`
table here or turn the pragma on and wonder why Phase 3's tests started failing.

unambiguous; state that in the docstring and note that plan 03-01's schema test is what keeps it
true. Every read decodes the stored JSON and every write encodes it. Each tier stores **only**
overrides: absence of a row means "inherit", and there is no sentinel value meaning the same thing.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| VisoMaster layout dicts → `schema.json` | GPLv3 source executed on a developer machine to produce a file committed into this repository. Executing it imports arbitrary upstream module-level code. |
| `schema.json` → loader → every consumer | One committed file becomes the sole authority on the type of every setting for the backend, the engine and the frontend alike. |
| caller → settings store | Project ids, face keys and settings keys arrive from callers that in Phase 4 are HTTP handlers, and reach SQL and a filesystem-derived directory listing. |
| models directory → option list | Filenames read off disk become option values a user can select and a later phase turns into a model load path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | SQL built around caller-supplied project id, face key or settings key | high | mitigate | Every statement in `store.py` uses bound parameters, never string interpolation, including in the `IN`-style lookups. A test asserts a project id containing a quote and a statement terminator round-trips as data and leaves the tables intact. |
| T-03-02 | Spoofing | An unknown settings key written into a tier table | medium | mitigate | Writes reject any key absent from the schema.
