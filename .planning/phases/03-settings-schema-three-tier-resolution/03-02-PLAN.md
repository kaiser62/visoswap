<measured_facts>
Measured during planning against the vendored tree and the reference web UI. Plan against these.

**The engine already has the matcher, and it is not a plain cosine distance.**
`visoswap/processors/models_processor.py:369-373` defines `findCosineDistance`, which flattens both
vectors, takes `1 - cos` into the range 0 to 2, and returns `100 - cos_dist * 50`. That is a
**similarity score on a 0-to-100 scale**: identical vectors score 100, orthogonal ones score 50,
opposite ones score 0. It is compared with `>=` against `SimilarityThresholdSlider`, a project-tier
int with range 1 to 100 and default 60 — at `frame_worker.py:151`, `:230` and `:284`. Reimplementing
this as a 0-to-1 cosine similarity and comparing against a 0-to-1 threshold would appear to work and
would match at a completely different tightness.

**The recognition model is chosen at the global tier, the threshold at the project tier.**
`frame_worker.py:139` passes `control['SimilarityTypeSelection']` and
`control['RecognitionModelSelection']` — both global — into recognition, then compares against
`parameters['SimilarityThresholdSlider']` — project. So an identity is only comparable against
another embedding produced under the same recognition model, and the stored identity has to record
which model produced it.

**`EngineContext.parameters` is already a per-face mapping.** `frame_worker.py:147` reads
`self.parameters[target_face.face_id]` — the full project-tier dict *for that target face*, not one
global set. Four sites index it that way. So the resolved output of this plan is not an abstraction
that Phase 4 has to adapt: it is literally the value that goes into that mapping under each face's
key. A key missing from the resolved dict raises inside the swap loop rather than falling back.

**`findCosineDistance` needs no instance state.** It reads only its two arguments, so it can be
called unbound for a cross-check without constructing a `ModelsProcessor` and loading 12 GB of
weights. Importing the module still requires torch, so the cross-check has to run on the engine
interpreter as a subprocess, which is the pattern `tests/conftest.py` already established for the Qt
probe.

**The web UI's face tier is index-keyed and volatile.** `webui2/app.js:102` seeds
`faceOptions[index]` from the parameter defaults; `:123` reads it by `selectedTarget`, an index;
`:186` writes it by the same index; and `:258`, `:283`, `:748` and `:778` clear the whole mapping.
Lines 746-754 attempt to carry entries across a re-detect by index, which is precisely the operation
that silently attaches face 0's settings to a different person when detection order changes.

**Gating is presentational.** Measured in plan 03-01 and restated because this plan is where it
could be got wrong: `frame_worker` reads a gated key's value unconditionally and reads the parent
toggle separately. Resolution must never filter by visibility. 140 keys carry a toggle gate, 4 carry
a selection gate, 8 keys have a parent that is itself gated, the deepest chain is 2, and there are no
cycles.

**Value types across the key set, from the schema:** 93 int, 43 toggle, 42 float, 22 selection, 1
text — 201 total, 168 project and 33 global, zero overlap. Bounds exist on 135 keys; the single text
key carries character-count bounds instead. 21 of the 22 selection keys carry a literal option list
of strings; the twenty-second resolves its list from the models directory at load.
</measured_facts>

Write `visoswap/settings/faces.py`: the layer that turns a recognition embedding into the stable face
key the face tier is stored under. Standard library only — no numpy, no torch — so it is testable on
the plain developer interpreter and so importing settings never drags the inference stack in.

Store an embedding as raw little-endian float32 bytes using the standard library's typed-array
module, alongside the name of the recognition model that produced it. The dimension is recoverable
from the byte length so no separate column is needed. Say in the docstring that a float64 embedding
is narrowed to float32 on the way in, and why that is safe: the threshold this feeds is an integer on
a 0-to-100 scale, so seven significant digits is several orders of magnitude finer than the decision
it informs.

Provide the similarity function as a **default that can be replaced**. The default is a pure-Python
implementation of the engine's formula: flatten both vectors, take one minus their cosine, and map
that into the 0-to-100 scale by subtracting fifty times it from one hundred. Take an optional
callable so Phase 4 can pass the engine's own bound method and remove the duplicate entirely. Two
implementations of one metric is a real risk and the injection point plus the agreement test below
is how it is contained — say that in the docstring rather than leaving a reader to wonder why the
seam exists.

Provide identity resolution: given a project id, a recognition model name, an embedding and a
threshold, compare against every stored identity for that project **under the same recognition
model**, and return the key of the best match at or above the threshold, or `None`. Comparing across
recognition models is meaningless — the four models produce embeddings in unrelated spaces — so
filter by model in SQL rather than scoring and discarding, and make a mismatched model a miss rather
than an error, because a project whose recognition model was changed mid-flight has no stored
identities under the new model and that is a normal state, not a fault.

Provide identity registration: given the same inputs plus a caller-supplied key, insert the identity
when nothing matches, and return the existing key when something does. The caller-supplied key is
the content-addressed digest Phase 2's `FaceCard` derives from the embedding, which plan 02-02
recorded as needing exactly this replacement — exact-digest keying becomes threshold matching here,
with the digest kept as the key so a first sighting still produces a stable, content-derived
identifier rather than a counter.

Use the **project-tier similarity threshold key** as the threshold, not a new constant. That means a
user who loosens matching for swapping loosens it for settings identity too. That coupling is
deliberate — one notion of "same face" in the application is better than two that can disagree — and
it needs stating in the docstring and in `docs/settings-schema.md`, because the alternative reading
is that someone forgot to add a second setting.

    - A bool offered for an int key is rejected: `isinstance(True, int)` is true, so the naive check accepts it.
    - An int offered for a float key is accepted and comes back a `float`.

    - A non-bool offered for a toggle key is rejected, including the strings that spell true and false.
    - Text longer than the character-count maximum is rejected; text at exactly the maximum is accepted.

    - Lenient conversion of every default in the raw layout dicts produces the same value the schema already holds.
  </behavior>
  <action>
Write `visoswap/settings/validate.py` with **two** clearly separated entry points, because conflating
them is how the string round-tripping this phase exists to end would quietly come back.

Strict validation is for everything that arrives from a caller — in Phase 4 that means an HTTP
handler, in Phase 5 a control the user moved. It accepts a value only if it already has the type the
schema declares, then checks bounds, option membership and text length. A string is a rejection, not
an input to be repaired. Reject with a message naming the key, what was offered and what was
expected; a validation failure that says only "invalid" is a support conversation.

Lenient conversion is for migration only — plan 03-03's preset seeding is its sole intended caller.
It applies the same shape-derived coercion the schema generator applies, so a string that spells a
number becomes that number and a decimal string in an integral key survives via a float hop, then
runs the strict validator on the result. Nothing else in the codebase may call it, and the module
docstring should say so and say why: every value in `profiles.json` is a string, so migration
genuinely needs it, and any other caller reaching for it is re-establishing the old behaviour.

Both read type, bounds and options from the loaded schema and from nowhere else. No literal key name
appears in this module. A second hardcoded rule here is the type moving back out of the data.

Guard the two traps that make a naive validator wrong. `isinstance(True, int)` is true in Python, so
bools must be tested before ints in every branch or every toggle passes as an int and vice versa.
And an int is a perfectly good float input — reject `1` for a float key and the frontend has to send
`1.0` for a slider sitting at one, which no renderer does — so widen ints to float for float keys and
say that widening is deliberate.

Decide the step rule explicitly rather than by omission: a value that does not land on a step
boundary is **accepted**. The step is a renderer's increment hint, not a constraint, and upstream
never enforced it — `StrengthAmountSlider` steps by 25 over a range of 0 to 500, and three of the
makeup sliders step by 3 over 0 to 255, which does not even reach the maximum. Rejecting off-step
values would make legitimate stored values unwritable. Record that decision in the docstring where
the next reader will look for it.

Then route every write in `store.py` through strict validation — the global tier, the project tier
and the face tier alike. Plan 03-01 already rejects an unknown key at the boundary; this replaces
that narrow check with the full one rather than adding a second gate beside it. Reads validate too,
but on a read a failure means the stored data is already wrong, so raise with a message that says
which tier the offending row is in — a value that failed validation on the way out came from a
migration or a hand edit, and knowing which is the whole diagnosis.

Write `tests/test_settings_validation.py` covering every item in the behavior block. The last item is
the one that matters most and is easiest to skip: assert that lenient conversion of the raw string
defaults reproduces the schema's typed defaults exactly, which is what proves the migration path and
the generation path cannot disagree. Read those raw defaults from a small inline table of measured
examples spanning all five shapes rather than importing the layout dicts, which cannot be imported
without Qt.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → settings writes | Values and keys that in Phase 4 arrive over HTTP reach SQL, numeric comparison and a text length check. |
| recognition embedding → face identity | A float vector decides which stored settings a detected person receives. |
| stored rows → resolved settings dict | Rows written by migration or by a previous version are decoded and handed straight to the swap pipeline. |
| gate definitions → visibility evaluation | Recursive evaluation over data derived from upstream, whose shape could change. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-08 | Spoofing | Face identity collision serving one person's settings to another | high | mitigate | Identity is scoped to the recognition model that produced the embedding and matched at or above the same threshold the swap pipeline uses, so the settings layer and the swap agree by construction. The agreement test against the engine's own method is what keeps the two implementations from drifting; a match below the threshold creates a new identity rather than reusing the nearest. |
| T-03-09 | Tampering | Out-of-range or wrong-typed values reaching inference | high | mitigate | Strict validation against schema type, bounds and option membership on every write, and on every read so that data written before the check existed cannot slip through. Bools tested before ints so a toggle cannot pass as an int. |
| T-03-10 | Tampering | SQL injection through project id, face key or settings key | high | mitigate | Bound parameters everywhere including the model-name filter. A test writes a project id containing a quote and a statement terminator and asserts it round-trips as data with the tables intact. |
| T-03-11 | Denial of service | Unbounded recursion in gate evaluation | medium | mitigate | The evaluator tracks its visited chain and raises on a repeat rather than recursing. Measured data has no cycle and depth 2, so the raise is a change detector rather than a routine path. |
| T-03-12 | Denial of service | Identity resolution scanning every stored embedding per detected face | low | accept | Faces per project are a handful, not a corpus; the scan is filtered by project and recognition model in SQL first. Revisit only if a project ever accumulates enough identities to matter, which single-face targeting makes unlikely. |
| T-03-13 | Information disclosure | Recognition embeddings persisted to disk as biometric-derived data | medium | accept | The embeddings are of media the single local user supplied, stored in that user's own project database on that user's own machine, per PROJECT.md's single-user scope. They are never logged and never leave the machine. Record the storage in the docs so it is a known, stated fact rather than a discovery. |
| T-03-14 | Repudiation | A stored value that fails validation on read with no indication of origin | low | mitigate | Read-side failures name the tier the offending row sits in, which distinguishes a bad migration from a hand edit. |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs nothing; it uses `sqlite3`, `json`, `array` and `math` from the standard library. If an install becomes necessary, halt and require the package-legitimacy gate plus a blocking human checkpoint. |
</threat_model>
