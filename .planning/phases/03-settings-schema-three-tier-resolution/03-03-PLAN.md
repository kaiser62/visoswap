<measured_facts>
Measured during planning against `D:/Visomaster/profiles.json` and `D:/Visomaster/web_ui.py`. Plan
against these; do not re-derive them.

**The source file holds exactly 2 profiles.** Ids `6a24b3aa71d7` named `A` and `55fc87c18307` named
`with AUD`. Each carries an `options` object of **33** keys — the global tier, and it matches the
global key set exactly — and a `parameters` object of **168** keys, the project tier. Each also
carries `created` and `updated` as Unix timestamps.

**Value typing in the source is inconsistent between the two entries.** Profile `A` holds 138 string
values and 30 bools in `parameters`. Profile `with AUD` holds 136 strings, 30 bools and **2 ints** —
`SimilarityThresholdSlider` is the integer 20 and `StrengthAmountSlider` is the integer 150, while
profile `A` holds the same two keys as strings. Both `options` objects hold 20 strings and 13 bools.
So migration cannot type a value by looking at what type it currently is; it must type by shape, via
the schema, exactly as the generator does. This is the concrete case that makes lenient conversion
necessary and it is the reason it exists.

**Both profiles store the same swapper pair.** `SwapModelSelection` is `Inswapper128` and
`SwapperResSelection` is `128`, in both entries, under `parameters` — the **project** tier.

**The reassignment is at four sites and it is wrong in two separate ways.** `web_ui.py:372-373`
inside the defaults merge, and `web_ui.py:1199-1200` on the generation path, both assign
`SwapModelSelection` to `Inswapper128` and `SwapperResSelection` to `256`. Two problems. First, they
assign into the **`options`** dict, which is the *global* tier, while both keys are project-tier keys
that live in `parameters` — so the values were being written where nothing would read them as
settings for a face. Second, the forced `256` **contradicts the `128` both profiles saved**, on every
load, silently. The same pair also appears at `web_ui.py:232-233` inside that file's built-in
defaults and at `:252` and `:258` in its hand-written schema stub. None of those five sites is being
ported; the criterion is that no equivalent appears in this repository.

**Removing the reassignment changes rendered output, and that is the intent.** With it gone, both
presets swap at resolution 128 as stored rather than 256 as forced. `SwapperResSelection` offers
`128`, `256`, `384` and `512` with a default of `128`, and it is gated on `SwapModelSelection`
equalling `Inswapper128`. A user who wants 256 sets it and it persists. Say this in the summary; it
is the one user-visible behaviour change in the phase.

**Six keys carried an `exec_function` and the current serializer drops every one of them.**
`web_ui.py:648-664` skips any key whose name starts with that prefix, which is how the side effects
went missing without a trace. The six, with the function each pointed at:

  - `ProvidersPrioritySelection` → `change_execution_provider`
  - `nThreadsSlider` → `change_threads_number`
  - `VideoPlaybackCustomFpsToggle` → `set_video_playback_fps`
  - `ViewFaceMaskEnableToggle` and `ViewFaceCompareEnableToggle` → `fit_image_to_view_onchange`
  - `ThemeSelection` → `change_theme`

Only the first three need a handler. The two view toggles are still fully functional as settings —
`frame_worker.py` reads them directly at lines 73, 751, 757 and 1280 — and their callback only refit
a Qt image view that does not exist here. `change_theme` loads a Qt stylesheet; theming belongs to
the web frontend.

**A literal port of the thread handler would be a no-op, and this is the trap.**
`control_actions.change_threads_number` at lines 22-25 calls `video_processor.set_number_of_threads`,
empties the CUDA cache, and updates a Qt progress bar. `video_processor` is the module Phase 1
dropped whole — so porting the function faithfully produces something that does nothing at all while
looking correct. The right handler is the one `visomaster_headless.py:99` uses:
`models_processor.set_number_of_threads`. That method exists in the vendored processor at line 242.

**The provider handler is three calls, two of which survive.**
`control_actions.change_execution_provider` at lines 16-20 stops the dropped video processor, calls
`models_processor.switch_providers_priority`, calls `models_processor.clear_gpu_memory`, then updates
a Qt progress bar. The two middle calls survive and both methods exist in the vendored processor, at
lines 210 and 259.

**The custom-fps handler does the opposite of what its name suggests.**
`control_actions.set_video_playback_fps` at lines 52-55 runs only when the toggle is on **and** media
is loaded, and it writes the media's own frame rate **into** `VideoPlaybackCustomFpsSlider`. It seeds
the slider from the video; it does not apply the slider to playback. That slider is an int with range
1 to 120 and step 1, so a 29.97 fps clip cannot be represented exactly and a 240 fps clip cannot be
represented at all. Rounding and clamping are required and are a real, user-visible consequence of
the schema typing that key as an int.

preset. That is the correct behaviour for an override model and it should be stated in
`docs/settings-presets.md` rather than discovered.

Route every write through the store, so preset application is validated by the same rules as any
other write and cannot become a side door around them.

target object as an argument** and never import the engine — plan 03-02's scan asserts nothing under

method on the models processor, so nothing here needs torch at all.

Three handlers, each named after the setting rather than after the upstream function, because the
upstream names describe a Qt event and these describe an effect.

The provider handler asks the target to switch provider priority to the new value and then to clear
GPU memory. Upstream also stopped the video processor first; that module was dropped whole in Phase 1,

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `profiles.json` → committed seed | A file from a GPLv3 checkout, of unverified provenance from this repository's point of view, becomes committed data that seeds a database. |
| committed seed → presets table → project settings | Values flow from a file to a table to the settings a swap runs under. |
| caller → handler → models processor | A settings value becomes a call that changes the execution provider and thread count of a live inference session. |
| repository source → the reassignment gate | A scanner decides whether a whole roadmap criterion is satisfied. |
