**The reference suite is 113 tests. 112 pass. One hangs.**
`112 passed, 1 deselected in 34.95s` with the cancelled-recording test deselected. Run with it
selected, `pytest` produces no output at all and never terminates; killed at 180 seconds.

**The hang is at `recorder.py:283`, `await self._decoder.wait()`.** Located by running the test under
`pytest -o faulthandler_timeout=40`, which showed the main thread parked in `asyncio.run` at
`test_recorder.py:220`, and then by an instrumented standalone replay that reported the exact await:

```
File ".../backend/services/recorder.py", line 283, in aclose
    await self._decoder.wait()
File ".../asyncio/subprocess.py", line 137, in wait
    return await self._transport._wait()
File ".../asyncio/base_subprocess.py", line 255, in _wait
    return await waiter
```

**The mechanism, in five steps.**

  1. The test holds the frontier at `t = 3.0` with `grace = 0.0` and waits for 30 frames. The pump
     writes through `t = 3.0` and then parks in `_await_deadline`, because `3.1 + 0.0 > 3.0`. From
     that instant nothing reads the decoder's stdout again.
  2. The decoder keeps producing. Raw `bgr24` at 160x120 is 57,600 bytes a frame against a 64 KiB
     `StreamReader` limit, so the buffer passes the high-water mark almost immediately and flow
     control **pauses** the stdout transport. Measured on the real recorder at the moment the pump
     parks: `fd=1 disconnected=False paused=True closing=False`.
  3. `aclose()` cancels the pump, then calls `self._decoder.kill()` and, in the *same event-loop
     step*, `await self._decoder.wait()`. At that instant the child's exit has not been observed, so
     `BaseSubprocessTransport._wait()` appends a waiter and suspends.
  4. The child does die. `_process_exited` fires and sets the returncode — measured
     `proc.returncode=1`, `transport._returncode=1`. **The process is dead and the wait still does
     not return.**
  5. The appended waiter is only ever woken from `_call_connection_lost`, which `_try_finish` reaches
     only when `all(p.disconnected for p in self._pipes.values())`. The paused stdout pipe has no
     read outstanding, so EOF is never observed, `pipe_connection_lost` never fires, `disconnected`
     stays `False`, and the waiter is stranded for the life of the process. There is no timeout on
     that await.

**It is a race, and the current code loses it by construction.** Seven variants measured against a
real killed `ffmpeg` whose stdout transport was asserted paused first:

```
A today: kill(); await wait()                        HANG (12s timeout, rc=1)
B kill(); await sleep(0); await wait()               HANG (12s timeout, rc=1)
C kill(); await sleep(0.05); await wait()            OK   in  0.06s (rc=1)
D FIX kill(); stdout transport.close(); wait()       OK   in  0.00s (rc=1)
E FIX kill(); proc transport.close(); wait()         OK   in  0.01s (rc=1)
F FIX kill(); resume+drain to EOF; wait()            OK   in  0.01s (rc=1)
G MITIGATION kill(); wait_for(wait(), 3)             OK   in  3.01s (rc=1)
```

Read A against C: the difference is 50 milliseconds of unrelated sleep. `kill()` is synchronous and
`wait()` suspends immediately, so the loop never gets a chance to poll the process handle between
them — the current shape loses the race every time rather than intermittently, which is why this
reproduces reliably rather than flaking. Read B against C: a single loop yield is not enough. Read G:
a bounded wait *passes the test* while leaving the defect in place and costing the timeout on every
cancel; it is the answer the roadmap explicitly rules out.

**An eighth variant uses no private attributes and works.** Draining with the public
`StreamReader.read()` — `StreamReader._maybe_resume_transport` resumes the transport on its own once
the buffer falls below half the limit, so `resume_reading()` need not be called by hand:

```
H kill(); while await proc.stdout.read(65536): pass; await proc.wait()
   OK in 0.01s  drained=3398400 rc=1
```

D and E reach into `proc.stdout._transport` and `proc._transport`, both private. H does not. Prefer H.

**Why this is the only one of the fourteen recorder tests that hangs.** Every other test that starts
a pump sets the frontier to `1e9`, so `_await_deadline` never blocks and `_pump_frames` runs until
`stdout.readexactly` raises `IncompleteReadError` at clean end of stream — which means the pipe has
been read to EOF and `disconnected` is already `True` before `aclose()` kills anything. The cancel
path is the only path that stops the reader mid-stream. That is not a coincidence to note in passing;
it is the reason the fix belongs in the close path and not in the pump.

**The partial file is genuinely playable once the close path completes.** With the drain applied,
`test_a_cancelled_run_leaves_a_playable_partial` passes in **0.40 s**, including its
`_decodes(partial)` assertion. Measured mid-hang the partial is 28 bytes — an `ftyp` box and nothing
else — because the encoder's stdin is closed at `recorder.py:289-292`, *after* the decoder wait that
never returns, so nothing is ever flushed. The `+frag_keyframe+empty_moov+default_base_moof` design
the module docstring describes was working correctly all along; the file was empty because the close
path never got far enough to close a pipe.

**With the drain applied the whole reference suite is green:** `113 passed in 36.97s`, no skips.

**The two subprocess paths in `aclose()` are asymmetric, and that asymmetry is the defect.** The
encoder path at `recorder.py:285-299` already closes stdin first and wraps its wait in
`asyncio.wait_for(..., timeout=30.0)` with a `kill()` fallback. The decoder path at `:281-283` has
neither. Whoever wrote the encoder path had the failure mode in mind.

**`READ_TIMEOUT = 120.0` and `FRAGMENT_SECONDS = 2.0` already exist** at `recorder.py:46` and `:55`
and are the right constants to reuse rather than introducing new numbers.
</measured_facts>

| the shape inventory → future phases | A scanner decides whether a class of defect can recur in code not yet written. |
