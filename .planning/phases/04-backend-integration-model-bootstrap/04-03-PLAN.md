<objective>
Give the backend a model bootstrap that reads its own manifest, verifies what is on disk, and
refuses to start when a required model is missing — with the refusal happening at startup, before any
route can serve, rather than inside inference.

Purpose: this closes `BACKEND-01` and roadmap criteria 2 and 3. It replaces the current failure mode,
which is a `FileNotFoundError` several layers inside an ONNX session load on the first frame a user
asks for, with a refusal that names the missing file and the directory it looked in.

Output: a manifest view over the vendored model lists, a verifier that distinguishes absent from
present-and-wrong, a startup gate wired into the app lifespan, and a written record of why six of the
sixty-two tracked entries are not required.
</objective>

**All 56 `models_list` files are present; all 6 `models_trt_list` files are absent.** Resolved
through the `model_assets` junction: 56 present totalling **12,233,143,713 bytes (12.23 GB)**, and
these six absent:

**The six TensorRT entries carry no `url`, and they are the only six that do not.** Every one of the
56 `models_list` entries has the keys `model_name`, `local_path`, `hash`, `url`. Every one of the 6
`models_trt_list` entries has `model_name`, `local_path`, `hash` — **and no `url`**. Their
`local_path` interpolates `trt.__version__` into the filename, so the tracked name changes with the
installed TensorRT version. They are locally built engine caches, not downloadable assets.

**This is the plan's central problem and it is not a detail.** Read literally — "the tracked set is
`models_list` plus `models_trt_list`, which is 6 entries when `tensorrt` imports" — the backend on
this machine tracks 62 files, 6 of which are missing and 6 of which cannot be fetched, so criterion 2
fires on a completely working install and criterion 3 becomes unreachable. The two criteria
contradict each other on the only machine either can be tested on.

The resolution is a **stated rule**, not an exception list: an entry is *required* when something
could actually load it and something could actually supply it. The six fail both halves. They cannot
be supplied — no `url`, and `visoswap/models/downloader.py` needs one. And nothing can load them:
`visoswap/engine.py`'s constructor refuses `TensorRT` and `TensorRT-Engine` outright with a
`ValueError`, so the provider that reads a `.trt` file cannot be selected at all. A missing `.trt`
therefore cannot produce the mid-inference failure `BACKEND-01` exists to prevent, which is the exact
test of whether something belongs in the required set.

**A full hash pass over the present set costs about 7 seconds warm.** Measured:
`inswapper_128.fp16.onnx`, 277.7 MB, SHA-256 in 0.16 s — 1,786 MB/s on this machine's cache — which
extrapolates to **6.8 s for 12.23 GB**. A cold read will be substantially slower. That is affordable
on a first run and not affordable on every restart, which is what the design means by "on first run".

**`model_assets` is genuinely hash-correct.** `inswapper_128.fp16.onnx` hashed to
`6d51a9278a1f650cffefc18ba53f38bf2769bf4bbff89267822cf72945f8a38b`, matching its manifest entry
exactly. So criterion 3's "complete set (verified by hash)" is satisfiable against the existing tree
today, and criterion 2 needs a deliberately incomplete directory built in the scratchpad rather than
any damage to a real one.

**Hashing is stdlib; downloading is not.** `visoswap/models/integrity_checker.py` imports only
`hashlib` and reads in 128 KiB chunks. `visoswap/models/downloader.py` imports `requests` and `tqdm`,
prints to stdout, and blocks. Both are present in `.venv-clean` and `requests`/`tqdm` are pinned in
`requirements-engine.txt`. The verify path must not acquire the download path's dependencies.

**The downloader has two behaviours worth knowing before it is called.** It removes an existing file
whose hash does not match and re-downloads it, and it retries three times. It writes directly to
`file_path` with no temporary name, so an interrupted download leaves a truncated file at the final
path — which the next run detects by hash and removes, but which is present and wrong in the interim.
This is the same class of finding plan 02-04 recorded about the vendored CLIP downloader
(`clip.py:75-76`: mismatching file not deleted), and it belongs in `docs/model-bootstrap.md` for the
same reason.

**The design spec says 54 files; the manifest says 56.** `docs/specs/2026-08-21-visoswap-standalone-design.md`
under "Models" reads "URLs and hashes for all 54 files (12GB)". The 12 GB is right (12.23 GB
measured). The 54 is wrong. The manifest is the authority; record the discrepancy rather than
inheriting it.

**`MODELS_DIR` already has one consumer.** `visoswap/schema/__init__.py` resolves the models
directory as argument → `MODELS_DIR` → repository-relative `model_assets/`, and caches the DFM
listing per resolved directory. Plan 03-01's note to Phase 4 is explicit: wire
`visoswap.schema.dfm_models()` into the engine context rather than writing a second directory scan.
Whatever this plan does with `MODELS_DIR` must agree with that resolution order, not compete with it.

Write `visoswap/models/bootstrap.py`: verification and, separately, repair. Project-authored; add it
to `PROJECT_AUTHORED`.

Verification reuses `visoswap/models/integrity_checker.check_file_integrity` and must import nothing
else beyond the standard library and the manifest module. Assert that in a test by parsing the
module: if the verify path ever acquires `requests`, the startup gate stops being runnable on an

Three states, not two, and this is the whole point of the task. A missing file and a corrupt file are
different facts with different remedies, and the vendored downloader already conflates them by
deleting and re-fetching anything that fails its check. A truncated 12 GB download and a file
somebody replaced look identical to a presence check and identical to that downloader; they should
not look identical in the report a user reads. Treat zero bytes as absent rather than present, for
the reason plan 02-03 recorded about the swap-only baseline: an empty file satisfies `isfile` and
every reader answers it with nothing, so an existence check silently degrades into a comparison
against nothing.

Two modes. Fast checks presence and non-emptiness; full also hashes. The measured cost of a full pass
is about 7 seconds warm over 12.23 GB and materially more cold, so full-on-every-restart is not the
right default and skipping hashes entirely is not either. Give the result an explicit field saying
which mode produced it, so a caller — and the summary — cannot mistake a fast pass for a verified
one. Which mode startup uses is task 3's decision; here, both must exist and both must be tested.

instead. Record its two measured behaviours in `docs/model-bootstrap.md` — it deletes and re-fetches
