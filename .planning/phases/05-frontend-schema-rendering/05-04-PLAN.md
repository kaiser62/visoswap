<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> PUT /api/projects/{id}/settings | Dirty-only overrides leave the client; the backend validates every value (plan 02) — the client never assumes its own values are safe |
| browser -> POST /api/projects/{id}/presets/{preset} | Preset application is confirmed in the UI, but the backend still owns validation and atomicity |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-11 | Tampering | PUT overrides from dirty state | medium | mitigate | Client sends only dirty keys; backend store.set_project validates type/bounds/options per key and rejects with 400 + rollback (plan 02) — client errors surface as the documented save-failure banner, dirty state retained |
| T-05-12 | Tampering | preset apply confirmation bypass | low | mitigate | Apply only fires from the confirmed modal; the backend applies atomically in a caller-owned transaction and returns the report |
| T-05-13 | Spoofing | save/discard actions | low | accept | Single-user local tool; no auth in scope (PROJECT.md out-of-scope) |
</threat_model>
