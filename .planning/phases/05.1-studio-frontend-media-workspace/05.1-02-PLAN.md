<objective>
Give the application a face library that belongs to the machine, not to a project.

Purpose: today a project's `source_face_path` column exists but nothing writes it through an
API, and no face image has a home. D-03 makes the store global so one uploaded face serves
every project, and D-05 makes deletion honest: the user is shown which projects break before
anything is removed.

Output: a `facestore` service that owns the on-disk layout and the identity rule, a `faces`
router that is the only way in or out of it, an activation endpoint that binds a library face
to a project, and a delete path that refuses silently-destructive behaviour.
</objective>

<assumption_delta_decision>
**Seam:** D-04 keeps automatic single-target selection now and names manual per-target picking
as a planned follow-up ("1 for now, 2 later planned"). The singular-to-plural seam is the
project's one `source_face_path` column and `faceselect.choose_target`'s single returned index.

**Decision: add-alongside, on the response side only.**

`POST /api/projects/{project_id}/face` takes a singular request body (`{"face_id": "..."}`)
and returns `{"assignments": [{"target_index": 0, "face_id": "...", "thumbnail_url": "..."}]}`
— a list that today always has exactly one element, chosen automatically.

Rationale: making the *request* plural now would require the UI to enumerate and pick targets,
which D-04 explicitly defers, and would ship dead surface. Making the *response* an assignment
list costs one array wrapper today and means the follow-up phase adds a `target_index` field to
the request instead of breaking a response contract that the Player, the Media panel and the
Jobs tab will all be reading by the end of this phase.

**Not chosen:** *promote* (plural request now) — ships unreachable surface and invites the
frontend to build a picker D-04 defers. *No-change* (scalar response) — forces a breaking
response change on every consumer when the follow-up lands.
</assumption_delta_decision>

    Identity is content-addressed: `face_id_for` digests the uploaded bytes with

    failure must not fail an upload — log a warning and record the face with a null thumbnail
    URL, the same never-fatal posture `Recorder._export` takes.

    `list_faces` enumerates the store, skipping `.thumb.jpg` companions, and sorts by mtime
    descending. Each record carries `face_id`, `display_name` (the sanitized original filename),

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `POST /api/faces` | Untrusted multipart body and untrusted filename cross here. |
| browser -> `{face_id}` path parameter | Untrusted string that names a filesystem object. |
| `source_face_path` column -> `Engine.swap` | A stored path is opened by the engine on the GPU interpreter. |
| `DELETE /api/faces/{id}?force=true` | An irreversible filesystem and database mutation triggered from the browser. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-02-01 | Tampering | `face_id` path parameter | critical | mitigate | `facestore.face_path` validates against a 32-hex pattern and raises `UnsafeFaceId` before any path join; four traversal cases asserted (T-02-07). |
| T-05.1-02-02 | Tampering | uploaded filename | high | mitigate | The on-disk name is the content digest plus a suffix drawn from a five-member allowlist; the user's filename is retained only as a display string. |
| T-05.1-02-03 | Denial of service | unbounded upload | high | mitigate | The streaming loop raises 413 the moment `written` passes `max_upload_bytes` and unlinks the `.part`, copied from `projects.upload_source`. |
| T-05.1-02-04 | Denial of service | image decompression during thumbnailing | medium | mitigate | Thumbnailing is wrapped never-fatal; a decode failure logs and stores a null thumbnail URL rather than taking the request down. The 413 bound applies before any decode. |
| T-05.1-02-05 | Information disclosure | absolute paths in responses | high | mitigate | `_public` continues to pop `source_face_path` and now emits `source_face_id`; a test asserts no response body contains the data directory path. |
| T-05.1-02-06 | Repudiation | silent cascade delete | high | mitigate | Deleting a face in use requires an explicit `force`; the unforced call returns a machine-readable 409 listing every affected project (D-05). |
| T-05.1-02-07 | Elevation of privilege | engine opens an attacker-chosen path | high | mitigate | `source_face_path` is server-assigned only — it is written solely by the activation endpoint from a validated face id, and `ProjectUpdate` continues to refuse it from the client. |
| T-05.1-02-08 | Spoofing | face id collision | low | accept | A 16-byte blake2b digest; a collision would require deliberate construction and yields only the ability to alias one's own uploaded face. |
