<objective>
Make the swapped frame appear over the playing video, and make it impossible for that
overlay to slow the video down.

Purpose: this is the product's core value — "real-time playback with asynchronous
predictive frame generation". Everything else in this phase is scaffolding around it.
The backend already generates ahead of the playhead, already indexes frames by
timestamp, already emits a completion event per frame, and already answers the
nearest-previous question. Nothing in the frontend consumes any of it: today's app is a
settings editor that has never rendered a generated frame.

The failure mode to design against is not "no frame" — it is a frontend that waits for
one. A per-frame fetch, an await in the render path, or an overlay that gates the video
element would each turn a working backend into a stuttering player, and would look like
an engine problem.

Output: a typed socket client that reconnects and refetches instead of trusting itself,
a frame index with a nearest-previous lookup, a media state container modeled on the
settings one, and a player card whose overlay is a positioned image that swaps when a
frame is ready and does nothing at all when one is not.
</objective>

  <behavior>
    - `buildIndex` over a frames response keeps only completed entries, sorted ascending by timestamp, each carrying its url.
    - `frameAtOrBefore(index, t)` returns the entry with the greatest timestamp less than or equal to `t`.
    - `frameAtOrBefore` returns null when every entry is in the future, and null on an empty index.
    - `frameAtOrBefore` is a binary search: it returns the correct entry on an index of ten thousand entries without scanning.
    - `upsert(index, entry)` inserts a newly completed frame in sorted position and replaces an existing entry at the same timestamp.
    - The socket client dispatches each parsed message to the supplied handler and silently discards the heartbeat frame.
    - The socket client reconnects after a close with a bounded backoff and invokes the supplied refetch callback on every successful open, including the first.
    - The socket client stops reconnecting once closed by the caller.
    - A malformed message body does not throw out of the client and does not stop the connection.
  </behavior>

    returning the greatest entry at or before the queried time, and null when there is none.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend socket -> reducer | Server-sent JSON drives client state transitions. |
| backend frame urls -> overlay image source | Server-supplied strings become an image source attribute. |
| browser -> `POST /api/projects/{id}/playback` | Client-reported position steers the scheduler's generation window. |
| browser -> `POST /api/projects/{id}/scheduler/start` | Client-chosen range starts GPU work. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-05-01 | Tampering | socket message parsing in ws.ts | medium | mitigate | Every frame is parsed inside a guard and dispatched only when its type matches the union; an unparseable or unknown frame is discarded without throwing and without changing state. |
| T-05.1-05-02 | Tampering | frame url used as an image source | medium | mitigate | The overlay only ever uses a url taken from the index entry the backend produced; no client string is concatenated into it. The backend already validates the timestamp key and containment in `get_frame`. |
| T-05.1-05-03 | Denial of service | a saturated or hostile event stream | medium | mitigate | The hub already drops events for a slow subscriber; the client adds a bounded reconnect backoff so a flapping socket cannot spin, and treats the refetched index as truth. |
| T-05.1-05-04 | Denial of service | unthrottled position reporting | medium | mitigate | One post per throttle window during play plus one per seek; each is fire-and-forget and cannot queue behind the render path. |
| T-05.1-05-05 | Denial of service | client-chosen generation range | medium | mitigate | The range duration bound is enforced server-side by the start model; the client refuses an inverted range before posting. |
| T-05.1-05-06 | Repudiation | overlay showing a frame from a previous face | high | mitigate | The per-start wipe plus plan 01's hot-swap purity test guarantee no stale frame exists to index; a reconnect replaces the index wholesale rather than merging, so a stale entry cannot survive a run change. |
| T-05.1-05-07 | Information disclosure | socket exposing another project's events | low | mitigate | The socket path is per project and the endpoint validates the id and closes on an unknown one; the client opens exactly one socket for the open project. |

No package-manager install task exists in this plan — `frontend/package.json` is unchanged — so no package-legitimacy checkpoint applies.
</threat_model>
