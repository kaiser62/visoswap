<objective>
Give the user the two things the player cannot work without — a video and a face — and the
three ways to run it.

Purpose: after plan 05 the overlay works, but nothing in the interface can put a video or a
face on a project; both still require a direct API call. Plan 02 built the face store and
plan 03 built the preview endpoint, and neither has a surface. This plan is where the
workspace becomes usable by a person.

Two of these are more delicate than they look. Deleting a face is a cross-project action:
the store is global, so a delete the user thinks is local can silently break three other
projects — hence D-05's requirement that the dialog name them before anything is removed.
And automatic preview is a request generator sitting on top of a settings panel with 201
controls: undebounced, or unaware that the video is playing, it becomes a queue of GPU work
competing with the run.

Output: a Media card holding video ingest and the face strip, a delete dialog that shows
consequences before it accepts them, a three-way mode selector wired to the range marks, and
a preview control that knows when to stay quiet.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local file picker -> `POST /api/faces` | Arbitrary local bytes cross into a machine-global store shared by every project. |
| local file picker -> `POST /api/projects/{id}/source` | Arbitrary local bytes become the project's video. |
| URL field -> `POST /api/projects/{id}/url` | A user-supplied remote address is fetched by the server. |
| delete affordance -> `DELETE /api/faces/{id}` | A local action has consequences in other projects. |
| preview toggle -> `POST /api/projects/{id}/preview` | A UI state change schedules GPU work. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-06-01 | Tampering | face and video upload filenames | critical | mitigate | The client never chooses a stored name. The face store derives its name from the content digest and the video upload path sanitizes server-side; both are the T-02-07 boundary and both were tested in plans 02 and 03. The UI sends bytes and displays server-returned identifiers. |
| T-05.1-06-02 | Denial of service | oversize upload | high | mitigate | Client-side size guard against the configured limit before sending, plus the server's existing 413; the guard is asserted to make zero requests. |
| T-05.1-06-03 | Denial of service | automatic preview queueing GPU work | high | mitigate | Debounced, gated on paused playback at fire time, gated on no active run, off by default, and refused server-side with 409 while a run is active. |
| T-05.1-06-04 | Repudiation | a delete silently breaking other projects | high | mitigate | Usage is fetched before the dialog offers confirmation; the affected project names are rendered; the confirm control does not exist until usage is known. |
| T-05.1-06-05 | Tampering | server-side request forgery through the URL field | high | transfer | The remote-fetch path is pre-existing and owned by the ingest service shipped in Phase 4; this plan adds a field over it and no new fetch behaviour. Recorded here because the field is new to the interface even though the surface is not. |
| T-05.1-06-06 | Information disclosure | face thumbnails served to any local reader | low | accept | Single-user local application (REQUIREMENTS.md "Out of Scope": multi-user, auth, hosting); the images are the user's own and already sit in a local folder. |
| T-05.1-06-07 | Spoofing | a face image that is not an image | medium | mitigate | The store validates the suffix against its allowlist and the thumbnail step fails soft; the UI surfaces the server's rejection message rather than assuming success. |

No package-manager install task exists in this plan — `frontend/package.json` is unchanged — so no package-legitimacy checkpoint applies.
