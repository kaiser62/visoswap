## What was built

**Task 1 — the scale knob reaches the engine.** `visoswap/engine.py` gained a private
`_processing_frame` helper and `swap(..., target_width=None)`: the decoded frame is
resized down before the worker runs and the result is resized back to native before it
is returned, so nothing downstream ever sees a frame change size mid-run. The engine
backend now passes the width the scheduler's own `_processing_width` computes; that
helper existed already but only ran on the source-frame-extraction branch, which is
exactly why the setting had been inert. The public surface test pins method *names*, so
adding a keyword argument did not widen the published API — checked before the edit, as
the plan required.

`tests/_engine_runner.py` gained a `--scale` mode reporting shapes and timings at full,
three-quarter and half width; `tests/test_engine_scale.py` (7 cases) asserts native
dimensions come back at every rung, that an oversize target never upscales, that an odd
target is rounded to an even width, and that half width is faster than full.

**Task 2 — measured, then labelled.** `tools/benchmark_engine.py --scale --idle-gpu`
measures full width twice plus three-quarter and half in one process, so the run-to-run
spread bounds what any difference is allowed to mean. It refuses to run without the
idle-GPU acknowledgement (verified: exit 4). The recorded run on the 1080p fixture,
CUDA, 20 timed swaps per rung:

| Rung | width | mean ms | fps | ratio to full |
|------|-------|---------|-----|---------------|
| full | 1920 | 56.07 | 17.84 | 1.000 |
| full (repeat) | 1920 | 55.32 | 18.08 | 0.987 |
| three-quarter | 1440 | 54.00 | 18.52 | 0.976 |
| half | 960 | 47.59 | 21.01 | 0.860 |

Spread 1.36%. **Half width is a real but weak lever — 14%. Three-quarter width is inside
the spread and is not a lever.** Detection and the swap model run at fixed input sizes,
so shrinking the frame only cheapens decode, resize and paste-back. That verdict is in
`docs/benchmark-baseline.md` under "Rung b", and the UI control quotes it verbatim —
no badge implies a speedup that was not measured (D-14). The percentage choice persists
to the project row, because the row is what the generator reads.

**Task 3 — the whole workspace against the real backend.** `frontend/e2e/studio.spec.ts`
drives one browser against real FastAPI and the real engine: empty states, ingest,
preview without starting a run (D-09), a bounded interval run leaving a partial take
under the derived name (D-12), and a gallery round trip asserting the 201 controls are
never unmounted (D-02). It uses the same local, gitignored fixtures the sealed runner
uses and fails naming the path it wanted rather than skipping.

## Deviations

- **Rule 2 (in-scope fix): `time.monotonic` hid the effect.** All three rungs first read
  identically at 0.078 s. Windows' `monotonic` ticks at ~15.6 ms, quantizing them onto
  one number. Switched to `perf_counter` and best-of-3 per rung. The coarse clock was
  hiding a real difference, not the test being wrong.
- **Rule 2 (in-scope fix): the gallery never re-listed.** The e2e run found a real
  defect — `GalleryView` fetched once on mount, and both views stay mounted for the
  control-count invariant, so a take created after page load never appeared. Now it
  re-lists whenever it becomes the visible view.
- **Out of scope, reported not fixed:** `tests/test_engine_deferred_paths.py::
  test_ledger_counts_are_consistent` fails (`assert 1 == 0`) because
  `.planning/WINDOWS.md` carries `open_count: 1` from plan 05.1-04. Pre-existing.
- **Noted:** `src/test/preview-modes.test.tsx`'s auto-preview-after-face-change case is
  load-flaky under a fully parallel run (fake timers plus debounce); it passes alone and
  passed in the final full runs. Not caused by this plan's changes — the suite was green
  both with and without the new file on the repeat runs.
