# Phase 05.1: Studio Frontend Media Workspace - Context

**Gathered:** 2026-08-23
**Status:** Ready for planning (after mandatory pre-work benchmark — see D-11)

<domain>
## Phase Boundary

The frontend becomes the whole application on **one page at `/`**, laid out after the user's VisoMaster Studio build (`D:/Visomaster/webui2`, dark card-grid design): load a target video (file upload or URL/local path), manage a **global face library** and activate one face per project, watch **live overlaid playback** where generated frames paint behind the playhead as they land (priority 1), preview the current frame on demand plus auto-preview on changes, **export a range or the full video**, and use three explicit generation modes (Stream-Live default / Export / Interval-N). Periphery in scope: **Jobs tab**, **Final Results card**, **Gallery page**. The existing 201 schema controls stay embedded in the Controls card (sidebar + groups unchanged). Backend work happens only where a UI capability has no endpoint yet (face-library endpoints, one-shot preview endpoint, gallery listing); the engine seam itself is not modified except where noted in D-04.

**Depends on:** Phase 5 (frontend scaffold, settings rendering, Playwright harness) — complete. Phases 2–4 backend (source bind, streaming, scheduler, frames, ws, recorder output) — complete.

</domain>

<decisions>
## Implementation Decisions

### App shell & layout
- **D-01:** **One page at `/`** — player, media/faces, Controls, results all on a single page in the webui2 Studio layout. No `/studio` route, no separate settings surface; today's settings app is absorbed into the Controls card. — **Reversibility:** reversible
- **D-02:** The Controls card **keeps today's mini-sidebar + scrolling schema groups exactly as-is**; tabs are added only for non-settings content (e.g. Jobs). Schema groups do NOT become tabs. The render-count gate (exactly 201 `[data-key]` elements) survives because all controls stay rendered. — **Reversibility:** reversible

### Faces
- **D-03:** **Global face library** shared by every project (modeled on the user's old `inputt` folder): a thumbnail strip, click-to-activate, active choice stored per project (`source_face_path` points into the global store). Requires new endpoints (upload / list / delete / activate) and a machine-global storage location. — **Reversibility:** costly — new public API surface plus an on-disk store other projects will reference
- **D-04:** Target selection stays **automatic** this phase: confident-female-first then largest-area (existing `faceselect.choose_target`), deterministic per video. **Manual picking of the target from detections is planned follow-up work immediately after this phase** (user: "1 for now, 2 later planned") — it will need detect-with-boxes plus target-index plumbing through the engine seam; plan 05.1 must not foreclose it.
- **D-05:** Deleting a global face that projects still point at: **warn + cascade** — the dialog lists affected projects; confirming deletes the file and those projects fall back to the "pick a face" no-source state. No orphan files.

### Playback & export
- **D-06:** **Full live overlay is priority 1**: while the video plays, swapped frames replace the current frame behind the playhead as they arrive (ws event driven); playback never pauses, waits, or stutters when a frame is missing (PROJECT.md core value). The export path ships in the same phase.
- **D-07:** **Three explicit user-facing modes**: **Stream-Live (default)**, **Export** (range or full), **Interval (N seconds)** — surfacing the backend's `generation_mode` stream/interval plus `SchedulerStart`'s full-video and range fields as distinct choices rather than hidden settings.
- **D-08:** Export covers **Set Start / Set End range and full video** (transport buttons like webui2; `range_start`/`range_duration`/`full_video` already exist server-side).
- **D-09:** **Preview Current Frame button + auto-preview**: renders the swapped frame at the playhead on demand and re-renders automatically when settings or the active face change while paused (webui2 parity). Needs a small one-shot preview endpoint that does not start the scheduler. No auto-preview during active playback.
- **D-10:** Periphery **in scope**: **Jobs tab** (current/all jobs from existing frame status + ws data), **Final Results card** (shows `.part` while recording via its complete flag, finished mp4 after, with download), **Gallery page**. **Video Library grid is deferred.**

### Process gates
- **D-11:** **Mandatory two-tier benchmark BEFORE any implementation starts**: Tier 1 — engine swap fps + per-frame latency at source resolution and 1080p on the CUDA provider via the sealed runner; Tier 2 — scheduler in stream mode over a real clip measuring generated frames/min against video fps (the number that decides whether live overlay can keep up). Results are written to `docs/benchmark-baseline.md` and cited by the plan. (User mandate: "before starting work, you need to benchmark".)
- **D-12:** **Save-on-stop, ported from the predecessor recorder verbatim in spirit** (user's actual workflow, evidenced by `D:/Dev/visomaster_live/output/*` filenames and `visomaster_live/backend/services/recorder.py::_export/_stem`): every run close — clean end OR user stop — exports the recording to an output folder as **`{project}_{YYYYMMDD-HHMMSS}_{face}.mp4`** (sanitized parts, empties dropped, collision-numbered, `.partial` suffix when stopped early, gated by an include-partials setting). Exports **accumulate** as the project's take history; the next start wipes only the working `output.mp4(.part)` cache, never the exported takes. The recording itself substitutes generated frames onto the original video timeline (`frames_substituted` counted). Final Results card shows the live `.part`; Gallery lists the exported takes with download. Export failures must never fail the run.

### Session addendum — hot-swap, threads, performance ladder
- **D-13:** **Face hot-swap on the same project is first-class**: stop generation, change the active face, start again — no project recreation. Purity is guaranteed by the existing per-start wipe (frames + cache + recorder output); with the D-11 embedding cache keyed by path+mtime, face changes can never leak across runs. Plan task: verify stop→change→restart end-to-end; decide whether stopping should also purge immediately rather than leaving prior-run frames visible until restart.
- **D-14:** **Thread count measured irrelevant** on the single-frame path (8 vs 1 threads within noise, both before and after embed-cache). Keep `nThreadsSlider` exposed at fixture default (2); never advertise it as a speedup.
- **D-15:** **Performance ladder, each rung behind its own bench gate**: (a) source-embedding cache → measured 10.3 fps floor @1080p; (b) `processing_scale`/`processing_width` exposure + bench variant (plumbed scheduler-side); (c) optional TensorRT spike behind an absolute cache path (T-02-09 made safe) — unverified legend until benched; (d) cadence honesty: nearest-previous overlay + interval modes + generated-vs-played ratio in Jobs tab. Live parity at 1080p24 is NOT promised in this phase.

### the agent's Discretion
Overlay rendering mechanism (canvas compositing vs positioned image swap) provided playback never blocks; appbar composition details (status pill, New button placement); empty states; auto-preview debouncing; face-store layout/thumbnail sizing; benchmark clip selection (any convenient local clip; assets may come from the user's machine, never committed if large).

</decisions>

## Specific Ideas

- The visual target is explicitly the user's own webui2 build — match its structure and tokens, not a new design.
- Live overlay is the headline: the user called both playback options desirable with overlay as "Priority 1".

- Benchmark numbers gate implementation start — they tell us whether stream-live overlay can keep up at 1080p before UI code is written against that assumption.
